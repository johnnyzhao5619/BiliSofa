# ADR-112 设备测量：来源检查并行与叠加层、评论复用（0.59.0）

2026-10-26。用户授权签名、安装0.59.0，要求按ADR-112先在已安装的0.58.0上测基线，再测0.59.0。

- **设备**：Samsung UN58U8200FFXZC，Tizen 9.0，登录状态。
- **包**：0.59.0未签名`016615d2…17ee`（与提交的候选一致），签名`74a3d488…153a`（证书预检PASS，权限不变）。升级安装、启动均platformSuccess（一次，不清数据）。

## 方法

脚本[ab.mjs](ab.mjs)，经Inspector驱动，每个版本测两轮，每轮首页6张卡，共12次起播：

1. 按“播放”起计时，逐次记录状态行的变化：
   - “正在获取播放源”出现的时刻；
   - “缓冲中”出现的时刻；
   - 首帧（`PLAYING`且时间大于0）；
   - 首条弹幕（`.danmaku-line`）。
2. 账号保存的弹幕设置是“关”：在同一个轮询里，一读到“弹幕 关”就切到“开”，离开前切回。与上次不同，阶段从按“播放”的那一刻就开始记录，不再漏掉第一阶段。
3. 首帧后2 s打开评论，计到第一张评论卡片出现。

注意：

- 推荐流每次启动内容不同，两个版本测到的不是同一批视频。
- 有观看记录（按续播）的次数：0.58.0为4次，0.59.0为8次。
- 只记录耗时、标志与应用自己的状态文字，不记录标题、ID或地址。

## 结果（中位数，n=12）

| 指标 | 0.58.0 | 0.59.0 | 变化 |
| --- | --- | --- | --- |
| 按播放到“正在获取播放源” | 3023 ms | 3089 ms | 不变（不是本批的目标） |
| “正在获取播放源”到“缓冲中”（含来源检查与播放桥） | 1344 ms（1065–3530） | 1368 ms（940–2055） | **无明显变化** |
| “正在获取播放源”到首帧 | 5280 ms（4430–9505） | 5618 ms（5108–8085） | 无明显变化（差异在波动范围内） |
| 按播放到首帧 | 8555 ms | 8626 ms | 无明显变化 |
| 首帧到首条弹幕 | 3495 ms（3143–20243） | **2936 ms**（2418–4715） | −0.56 s（−16%） |
| 打开评论到第一张卡片 | 3687 ms（3492–4116） | **3219 ms**（2860–3351） | −0.47 s（−13%） |

原始数据：[0.58.0 a](ab-0.58.0.json)、[0.58.0 b](ab-0.58.0-b.json)、[0.59.0 a](ab-0.59.0.json)、[0.59.0 b](ab-0.59.0-b.json)。

0.58.0有一次首帧到首条弹幕为20.2 s，很可能是该视频开头几秒没有弹幕。所以只比较中位数。

## 成对检查确实在运行，但没有变快

用[pairprobe.mjs](pairprobe.mjs)挂到播放源Worker上，统计一次起播中的调用（只记次数与耗时）：

| 起播 | 成对检查调用 | 单项检查调用 | 成对检查耗时 | “获取播放源”到“缓冲中” |
| --- | --- | --- | --- | --- |
| 1 | 1 | 0 | 未计时 | 1668 ms |
| 2 | 1 | 0 | 545 ms | 867 ms |
| 3 | 1 | 0 | 1484 ms | 1882 ms |

- 设备上走的是成对检查，没有退回逐项检查。
- 成对检查占了这一阶段的大部分时间，但并行没有缩短它。
- **推断**：视频与音频轨通常在同一个CDN主机上。
  - 0.58.0逐项检查时，第二项复用了第一项刚建立的TLS连接，几乎不再花时间；
  - 并行时，两路同时各自新建连接，总等待仍约等于一次握手。

  这一段的大头是第一次连接CDN，而不是两次请求相加。这一推断还没有用分项计时直接证明。

## 结论

- **B（复用绑定）有效**：首帧到首条弹幕−0.56 s，打开评论到第一张卡片−0.47 s。
- **A（来源检查并行）没有可测的收益**：功能正确，主备切换也照旧，但这一段的耗时没有下降。
- **可能的下一步**（不在本批，需要另行决定）：
  - 把来源检查提前到详情页预读阶段（与ADR-110的预读一起做），让连接在按“播放”之前就建立好；
  - 或让两路检查共用同一条连接（例如先查一路，复用连接再查另一路，这正是0.58.0的做法）。

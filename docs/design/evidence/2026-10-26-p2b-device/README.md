# ADR-116/117 设备验证：首页快照、分区直达、搜索综合与词典常驻（0.64.0、0.64.1），全站排行与依次读取（0.65.0）

2026-10-26。用户授权签名、安装0.64.0，在电视上测冷启动到首页第一张卡（有、无快照）和进入搜索后首个候选的时间，与0.63.0对比，并实看首页与搜索。

- **设备**：Samsung UN58U8200FFXZC，Tizen 9.0，登录状态。
- **包**：未签名`0dba7d8d…7523`，签名`bbd6f27b…9691`（只签一次，证书预检PASS，权限不变）。
- **安装**：升级安装、启动均platformSuccess（一次，不清数据）。

## 方法

脚本见[coldstart.mjs](coldstart.mjs)。每次测量前用`sdb shell 0 kill`结束应用，再调试启动一次（新进程）。

- **首页**：
  - 在“谁在观看”对已保存的账号发送OK（Inspector），计时到首页第一行出现第一张卡；
  - 同时记录这一行第一次出现非快照卡片的时间（即读取结果到达）。读到的第一张卡与快照相同时，这一项与第一张卡相同或记为未知。
- **搜索**（首页后等5 s，过了0.64.0词典预加载的3 s）：
  - 打开搜索，按N，计时到第一个候选可选；
  - 回首页后再进一次，清空后按N，再计一次。
- **快照条件**：
  - “无快照”：在按OK前删掉本机的首页快照键；
  - “有快照”：用的是上一次运行写下的快照。
- 各3次；0.64.0两种条件交替进行。
- 只记录时间与是否有快照，不记录卡片标题与编号。

## 结果

| 条件 | OK→第一张卡 | OK→读取结果到达 | 搜索首个候选 | 再次进入搜索 |
| --- | --- | --- | --- | --- |
| 0.63.0 | 2374 / 2422 / 2254 ms | 同左 | 600 / 576 / 598 ms | 544 / 591 / 531 ms |
| 0.64.0 无快照 | 2499 / 2351 / 2472 ms | 同左 | 213 / 186 / 168 ms | 80 / 123 / 116 ms |
| 0.64.0 有快照 | **1817 / 2042 / 2021 ms** | 2469 / 2707 / 2679 ms | 138 / 124 / 129 ms | 108 / 167 / 145 ms |

结论：

- **有快照**时第一张卡平均早出现约0.4 s（约1.96 s，对比0.63.0约2.35 s）。读取结果在约2.6 s到达，随后原位替换。
- 首卡仍要约1.8 s。我推测这段时间主要花在选账号之后的身份核对与页面建立上：首页要等它完成才挂载，所以快照只能省下后面的读取部分。这只是推测，这次没有分段计时。冷启动的大头不在列表读取。
- **无快照**时与0.63.0持平，说明快照的读写没有拖慢首页。
- **搜索首个候选**从约0.59 s降到约0.13–0.19 s，再次进入约0.08–0.17 s：词典常驻后不再每次重新解析约1 MB的数据。

原始数据：`cold-0.63.0.json`、`cold-0.64.0.json`。

## 实看（用户确认）

用户从电视主页正常打开0.64.0，选自己的账号，逐项确认都符合：

1. 进入首页时各行直接显示上次的卡片，不是骨架；稍后自动更新，焦点不乱跳；热门行末尾会自动多出卡片。
2. 排行榜下的一排分区按钮按OK直达，返回回到原按钮。
3. 搜索默认“综合”，视频上方有UP主与番剧影视各一行，“全部UP主”切到UP主页签。
4. 按第一个字母后候选出来得比以前快。

## 未覆盖

- 游客状态的首页快照（游客首页没有“为你推荐”行）。
- 快照过期（24小时）后的冷启动。
- 真实遥控器操作的计时（本次按键由Inspector发出）。

## 0.64.1复测：加载中的货架行可越过

用户授权签名、安装0.64.1：

- **包**：未签名`54b7e4a6…436a`，签名`81f9632d…b6f2`（只签一次，证书预检PASS，权限不变）；
- **安装**：升级安装、启动均platformSuccess（一次，不清数据）。

**方法**：

- [holdcheck.mjs](holdcheck.mjs)在“谁在观看”时删掉公共快照，并在页面里扣住含ranking的读取消息，让排行榜停在加载状态；
- 选账号进首页后，用[upcheck.mjs](upcheck.mjs)把焦点放到第一个分区按钮，发送受信任的上、下键；
- 只记录焦点所在行的类别与各行按钮数。

| 时刻 | 各行（按钮/骨架卡） | 分区按上 | 再按下 |
| --- | --- | --- | --- |
| 热门与排行榜都在加载 | 为你推荐5、热门视频0、排行榜0、分区14（这次只记了按钮数） | 为你推荐（越过两行） | 分区 |
| **热门已读完、排行榜仍在加载** | 为你推荐5/0、热门视频9/0、排行榜0/5、分区14/0 | **热门视频** | **分区** |

用户随后用遥控器实按并回答“符合”。但在把焦点交给用户前，排行榜已以`timeout`结束，显示为失败行（重试、查看更多），所以这次实按发生在失败行状态，不能当作“加载中”的证据。“加载中可越过”以上表的受信任按键为准。

**更正**：上面的`timeout`和“热门视频读取慢”都不是真实的读取慢，原因如下（调查见[ADR-117](https://github.com/johnnyzhao5619/BiliSofa/blob/a709767e0fd4b6eef741bd3193bafa6348ca0ff8/docs/adr/117-ranking-session-refusal-and-row-order.md)“背景”）：
- 首页各行要等焦点进到上一行才开始读取，冷启动后焦点在“继续观看”，所以下面几行的骨架卡停在那里，但读取并没有开始；
- 第二次复测时扣住一直没放开，排行榜请求在按上键、焦点进到“热门视频”后才发出，正好被扣住，公共内核12秒请求预算到期后报`timeout`；
- 记录到“扣住的读取为0”时，请求还没发出。

用[kernelwatch.mjs](kernelwatch.mjs)调试冷启动两次，只观察Worker消息，记录时刻、操作名、结果类别与API码：

- 登录状态打开分区1005（账号内核本人会话）：1.02 s成功。

同一网络的Mac对照（每次间隔约5 s）：
- 全站排行与分区排行在匿名、带访客cookie、WBI签名、WBI加访客cookie四种方式下都是-352；
- 热门视频为0。

结论与修复方向见ADR-117。

## 0.65.0设备验证（ADR-117）

用户授权签名、安装0.65.0，用kernelwatch同法观察登录与游客两种状态下的排行榜读取，并按ADR-114测首页方向键响应，与0.64.1对比。

- **包**：未签名`9b3f89e5…c82d`，签名`f83e83e5…f84c`（只签一次，证书预检PASS，配置只改版本号，权限不变）。
- **安装**：升级安装、启动均platformSuccess（一次，不清数据）。

### 排行榜读取

方法：
- 每次都是新调试启动；
- [kernelwatch.mjs](kernelwatch.mjs) `still`模式，选账号或“游客浏览”后不移动焦点，只观察Worker消息；
- 时间从按OK起算。原始记录在[0.65.0/](0.65.0/)。

| 条件 | 为你推荐 | 热门视频 | 排行榜（发出→结果） | 结果 |
| --- | --- | --- | --- | --- |
| 登录 ×1 | 1.88→2.53 s | 2.55→3.18 s | 3.19→3.89 s | 本人会话`ranking`，12张卡 |
| 登录 ×2 | 2.21→2.84 s | 2.86→3.87 s | 3.89→4.58 s | 同上 |
| 登录 ×3 | 2.06→2.70 s | 2.72→3.63 s | 3.65→4.39 s | 同上 |
| 游客 ×3 | — | 选择前已读（“谁在观看”下的游客首页） | 0.68–1.40 s发出，0.30–0.33 s后返回 | 匿名-352，保留快照并显示“显示的是上次的内容”，`title`为`limited` |

- 登录状态下三行严格依次读取，每次一行。三行都在按OK后3.9–4.6 s内读完，期间焦点没有移动。
- 每次选账号前，都停掉了一个进行中的公共读取（`stop`），即“谁在观看”下游客首页的第一行。依次读取在被页面盖住时不接着读，所以游客首页没有再读排行榜。
- **游客、无排行榜快照**（[guestretry.mjs](guestretry.mjs)：先在一次启动里删掉公共快照中的排行榜项，再新启动）：
  - 行内显示“B站暂时限制了访问（风控 -352），约 60 秒后可重试；登录后通常更稳定”；
  - 5 s后按“重试”，变为“约 55 秒后可重试”，期间没有新的排行榜请求（前后都是1次）。
- 这台电视当前的公共快照里已没有排行榜项，下次登录读取成功时会重新写入。

### 首页方向键响应（ADR-114同法）

方法：
- 新启动、选账号，等6 s后，从“热门视频”第一张卡右10左10；
- 快：间隔150 ms，5轮；慢：间隔600 ms，3轮；
- [keyspeed.mjs](keyspeed.mjs)：记录`keydown`到其后第二帧的时间，只记时间与次数。
- 0.64.1在安装0.65.0之前测。

| 条件 | 0.64.1 | 0.65.0 |
| --- | --- | --- |
| 快：中位数 / p95 / 最大（焦点移动的按键） | 35 / 54 / 67 ms（85次） | 38 / 55 / 76 ms（100次） |
| 快：每轮>50 ms帧 | 4.0 | 2.0 |
| 慢：中位数 / p95 / 最大 | 31 / 38 / 61 ms（51次） | 33 / 41 / 42 ms（60次） |
| 慢：每轮>50 ms帧 | 2.7 | 1.3 |

- 两版都没有超过200 ms的按键。中位数高约2 ms，在轮与轮之间的波动范围内；0.65.0的长帧更少。
- 0.65.0的最大值76 ms出现在第1轮，其余各轮在50–64 ms。
- **条件不完全相同**：
  - 0.64.1的“热门视频”是8张卡，即上次的快照；它在焦点进入“为你推荐”前不会刷新，测试直接把焦点放到热门，所以一直没有刷新，右键10次中有3次已到行尾不移动。
  - 0.65.0这一行已依次刷新为12张卡。
- 结论：依次读取没有带来可测的按键变慢。测量在按OK后6 s开始，这时三行已读完，所以这组数据不覆盖“读取进行中按键”的情况。

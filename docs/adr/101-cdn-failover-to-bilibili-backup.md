# ADR-101：播放源按轨道切换到B站备用线路

2026-10-23；F06/F17、R13、U5。接0.50.2真机P4″：伍六七之玄武国篇前三集仍然失败。画面两次出现“正在重新连接…”后停止，每次出错的位置都一样；其他视频可以播放。仅在`--product-cdn-failover`（0.50.3）构建生效。状态：**0.50.3已签名并升级安装/启动（平台确认，不清数据）；P4‴第1集PASS、第2/3集FAIL（读取播放源阶段），后续见文末与[ADR-102](102-source-check-failover-and-run-level-avoidance.md)**（[证据](../design/evidence/2026-10-23-cdn-failover/README.md)）。

## 原因

以下是匿名只读核对的结果，对象是第1集（免费，480P及以下）。第2、3集是会员集，没有用账号读取。

- B站播放接口给每条轨道一个主地址和一个备用地址：
  - 主地址多为海外节点`upos-sz-mirrorcosov.bilivideo.com`；
  - 备用地址是B站自己的Akamai节点`upos-hz-mirrorakam.akamaized.net`。
  - TS和原生的地址规则只接受`*.bilivideo.com`，所以备用地址一直被丢弃。
- 按桥接的方式每段读取2 MiB，完整读一遍：
  - **cosov**：视频前约8 MiB正常，之后的段大多15秒超时；音频同样如此。同一偏移重复测试，结果一致。单独计时：15–26秒内没有响应头，随后返回`504 Gateway Timeout`或很晚才到的206。这说明问题是节点回源失败，不是传输慢。
  - **Akamai备用**：同一文件14段全部成功，共18.7秒。
  - **对照**：社区客户端的做法是把主机换成其他国内镜像。实测也能读，但这些不是B站给出的地址，而且mirror08c不可达，所以不采用。
- 这解释了为什么“位置一致”：
  - 桥接遇到超时只对同一主机重试；
  - 0.50.2重连时从B站拿到的还是同一主机；
  - 画质回退换到的其他文件也在同一节点上。

## 决定

做法参照DASH的多BaseURL、ExoPlayer的`BaseUrlExclusionList`、dash.js的BaseURL切换，以及B站客户端对`backup_url`的使用。

- **地址规则**：
  - 在原有规则之外，只增加B站的备用主机族`upos-<1–16位小写字母或数字>-mirrorakam.akamaized.net`；
  - 仍要求https、不带端口、路径以`.m4s`结尾、有唯一的10位deadline；
  - TLS照常校验，随包CA能验证该证书链；
  - TS与原生的规则一致，两边都有测试。
- **每条轨道的地址**：
  - 主地址仍是第一个bilivideo地址，来源检查沿用未改的原生`vod-api`/`pgc-read`；
  - 备用地址是第一个通过规则、且主机不同的候选。
- **原生桥接**：
  - 新入口`vod-bridge-failover.c`，链接到新目录`build/vod-failover`。`vod-bridge.c`、`probe-bridge.h`、`vod-source-policy.h`和冻结的`build/vod`都不变，生成脚本在原有生产配方之上只做带核对的改写。
  - 某段满6秒仍无响应头、超时，或结果不是校验通过的206时，该轨道切到备用，并从同一段继续。已转发的字节不重放，总长必须一致。
  - 每条轨道只切换一次，切换后保持。之后沿用原有的有界重试和失败路径。
  - 备用地址只能缩短签名租期；续期时，备用地址的有无必须与之前相同。
- **本播放页内的排除表**：
  - 桥接切换后，来源Worker记下这个主机；
  - 同一页里之后的剧集、画质回退和重连，都直接从备用开始；
  - 按主机排除，不跨应用重启，不持久化。
- **诊断**：“帮助与诊断”的失败摘要追加上游HTTP状态/cURL代码，以及“已切换备用线路 N 次”，都是固定数字。
- **保留0.50.2的有界重连**，作为备用也失败时的最后一层。

## 不做

- 不改写主机，不加入其他第三方CDN或mcdn/PCDN节点，地址不进入页面或日志。
- 来源检查本身失败时，不改用备用地址：那需要改共享的原生模块，而目前没有出现过这种情况。

## 证据

- 原生主机测试`tests/native/vod-bridge-failover.test.py`，共6条，用真实socket和cURL：
  1. 地址规则只接受B站Akamai族；
  2. 主地址无响应头时，6秒内切到备用，字节逐一相同，且之后不再回到原主机；
  3. 206读到一半卡住时，从第一个未收到的字节在备用上继续；
  4. 起始位指定的轨道直接从备用开始；
  5. 没有备用时，行为与原来相同；
  6. 续期保留备用和已切换的状态。
  - 原有`tests/native/vod-bridge.test.py`仍为10/10。
- 单元`tests/unit/vod-cdn-failover.test.ts`：地址规则、主备配对、旧构建解析与原来相同、报价与排除表、诊断只保留数字。
- 合成UI`tests/product-cdn-failover-ui/failover.spec.ts`：
  - 经真实的来源Worker、桥接Worker和页面，桥接收到两条备用地址；
  - 切换一次后，重连从备用开始，不再切换；“帮助与诊断”显示切换1次。
  - 对冻结0.50.2失败；去掉排除表的变异版本也失败。

## 待真机

P4‴：连续播放伍六七之玄武国篇前三集，各看到原来出错的位置之后。若仍失败，报告“帮助与诊断”里的失败摘要（含“上游”与“已切换备用线路”）。

## 0.50.3真机结果（P4‴，2026-10-23）

- 第1集正常播放，说明桥接切换对播放中途的断流有效。
- 第2、3集（会员集）自动重连后仍失败。诊断为`phase: source`、`reason: network`，没有任何开始播放的记录，即失败发生在开播之前。
- 本ADR明确没有覆盖来源检查，失败正好落在这个缺口。处理见[ADR-102](102-source-check-failover-and-run-level-avoidance.md)。

# ADR-110：播放起播——详情页预读并交给播放器、续播直接从位置起播、按原因降级、叠加层复用会话

2026-10-25；F06/F08/F09/F10、R03/R09、性能。接2026-10-25 review与ADR-108/109。状态：**用户确认全部4项决定（2026-10-25）；P1-1a在0.57.0实现并已签名安装；设备对比0.56.0：续播首帧11.3→8.5 s、详情页停留3 s后播放8.3→5.3 s，立即播放无变化；0.57.1补上“缓冲中”并经设备确认；0.57.2让自动选择画质的说明与互动状态并列，经设备确认（见“设备结果”）。P1-1b的实现方案见[ADR-112](112-parallel-source-checks-and-overlay-binding-reuse.md)（0.59.0已实现并安装：复用绑定有效，来源检查并行无可测收益），其中第8项改为经私有绑定端口交接，常驻Worker暂缓**。改动方案见[P1-1方案](../plans/2026-10-25-p1-1-playback-start-plan.md)。

## 背景

从首页卡片到首帧，代码核对后的顺序如下（行号为2026-10-25的源码）：

1. **卡片 → 详情页。** `product-page.ts`第92行的`parts()`为了列出分P与简介，打开一个完整的`VodAccess`：新Worker＋WASM，再依次读nav→view→playurl。读完就关闭，playurl被丢弃。
2. **详情页 → 播放器。** 按“播放”后，要先等详情页那次读取的Worker关闭（`product-video-detail.ts`第54、138行）。播放器再打开一个新`VodAccess`（`vod-runtime.ts`第76行起），nav→view→playurl全部重读一遍。
3. **起播前检查与准备。** 视频与音频的512字节来源检查是**串行**的（`vod-native-api.ts`第173–176行，各10 s超时）。之后是播放桥Worker，再`prepareAsync`。
4. **续播。** 先在0处prepare，再seek到续播位置（`session.ts`第75–78行），开头那段白白缓冲了一遍。重新起播的路径（`avplay.ts`第107行）早已用`PREBUFFER_MODE`直接从指定位置准备，并有设备证据。
5. **降级。** prepare或播放失败时，只要原因是网络、超时或不支持，就降一档画质重试，最多4次（`vod-catalog-media.ts`第41行）。纯网络故障降画质并不对症，只会把等待时间放大好几倍。
6. **超时毒化。** 读取超时或播放桥启动超时会毒化运行时（`vod-runtime.ts`第66–70、133、199行），之后`reconnect-policy`的重连只会得到`unknown`。
7. **叠加层。** 弹幕元数据、字幕、每6分钟一段的弹幕，每次读取都新建一个Worker，并重新跑nav＋view来取aid/cid（`overlay-runtime.ts`第27行，`overlay-native-api.ts`第12–39行）；`OverlayTarget`只有`bvid/part`（`overlay-read.ts`第16行）。

一次登录状态下的起播，在弹幕出现前大约是：7次Worker＋WASM启动，nav 6次，view 6次，playurl 2次，`player/v2` 2次。

## 决定

分两批做。P1-1a不改原生，P1-1b改原生。

### P1-1a（不改原生）

1. **详情信息走公共内核，播放读取在详情页就开始。**
   - 分P、简介、点赞、弹幕数改由公共内核新增的“视频信息”请求读取（只读`/x/web-interface/view`）。复用常驻连接，不启动WASM。
   - 公共内核原来禁止`/x/web-interface/view`，现在改为只允许这一条；playurl、CDN与`player/`系路由仍然禁止。
   - 详情页打开的同时，在后台为当前分P打开`VodAccess`并完成读取（nav→view→playurl）。
2. **按“播放”时把这次读取交给播放器。**
   - 不关闭、不重读：详情页把已读好的`VodAccess`与结果移交给播放器，所有权从详情页的owner转到播放器的owner。
   - 预读还没完成时，播放器接过同一个进行中的读取。
   - 离开详情页且没有播放时，后台读取取消并关闭，和现在一样。
   - 换分P、或从“继续观看”进入其他分P时，交接前比对`bvid/part`，不一致就丢弃预读。
3. **续播直接从位置起播。** 有续播位置时，首次`open/prepare`就用`PREBUFFER_MODE`带上起始位置（与重新起播同一路径），不再先在0处准备再seek。
4. **降级按原因。**
   - 网络或超时：先用同一画质换另一条线路重试（播放桥已有主备，ADR-101/102），再失败才降画质；
   - 不支持（解码/格式）：直接降画质；
   - 总尝试次数仍不超过4次。
5. **超时缩短，且不毒化。**
   - 源Worker就绪与读取上限从45 s改为15 s；
   - 读取或播放桥启动超时只作废这一个`VodAccess`，重连时新建一个，不再让之后的重连都得到`unknown`；
   - 原生关闭仍要求确认：关闭未确认时，这个`VodAccess`照旧不复用。
6. **分阶段提示。** 加载期间依次显示：“读取视频信息”“获取播放源”“缓冲中”；换线路时显示“已切换备用线路”。不再全程只有一行“正在读取所选内容和播放源”。

### P1-1b（改原生）

7. **来源检查并行。** 视频与音频的512字节检查同时发出（`vod-api.c`增加第二个CDN句柄），总等待由两次相加变为取较长的一次。
8. **叠加层复用一个常驻Worker，并复用aid/cid。**
   - `OverlayTarget`增加可选的`aid/cid`，取自播放读取的结果；有了它们，原生直接读`player/v2`与弹幕分段，不再先跑nav＋view；
   - 一次播放只启动一个叠加层Worker（沿用ADR-108的常驻客户端），弹幕分段、字幕依次在同一会话里读取；
   - 评论同样复用aid，不再为取aid读view。

## 不做

- 卡片上按OK直接播放、播放器设置抽屉等交互改动（P1-2）。
- 在卡片获得焦点时预读：流量与风控代价不确定，先看P1-1a的实测效果。
- 默认画质与码率策略、ABR（另行决定）。
- 写入通道（点赞、投币、收藏、追番）与投屏通道。

## P1-1a实现（0.57.0）

- **视频信息**：
  - 公共内核新增11号操作，只读`/x/web-interface/view?bvid=`，Referer为视频页；
  - 结果放进独立的4 MiB缓冲（分P或合集很多的视频超过共享的512 KiB），列表请求仍用原缓冲；
  - 路由扫描放行view，同时禁止任何含`playurl`、`/x/player/`或`bilivideo`的路由；
  - 结果只带分P数、前48个分P、UP名与简介信息；
  - 详情页经`KernelVideoView`读取，10分钟复用。
- **预读与交接**（`vod-prefetch.ts`）：
  - 详情页一打开就为当前分P开始播放读取；
  - 按“播放”或该分P的按钮时，若同一视频同一分P、不超过5分钟、访问未关闭或毒化（新增的`VodAccess.usable()`，账号包装同样转发）、且读取没有失败，就把同一个访问与读取交给播放器；
  - 交出的打开函数只交接一次，之后再调用（例如重连）就新开访问；
  - 离开详情页且没有播放时，取消读取并关闭访问。
- **详情回退（实现中新增）**：视频信息读取失败时，详情页改用预读结果里的同样信息（分P、简介、UP），不再只显示“暂时无法读取”。
- **续播起播**：
  - 播放器后端新增`startsAt`能力，AVPlay在有`setStreamingProperty`时为真；
  - 有续播位置且后端支持时，首次`prepare`就带上起始位置（`PREBUFFER_MODE`）；被拒绝时退回“先准备再seek”；
  - 起播后第一次报告的时间若比续播位置早5秒以上（后端忽略了位置），补一次seek；
  - **更正**：背景里说的“有设备证据”只适用于投屏（MP4），点播DASH的这条路径没有设备证据，留待装机验证。
- **降级**：网络或超时先用同一音视频轨重试一次（播放桥会避开失败的主机），之后，或遇到不支持，才降一档画质；总次数仍不超过4。重试时状态显示“已切换备用线路，正在重试”或“已降低画质，正在重试”。
- **超时与重连**：
  - 源Worker就绪与读取上限45 s→15 s；
  - 重连时，访问已不可用就先关闭再新开，不再让后续重连都得到`unknown`。
- **分阶段提示**：依次显示“正在读取视频信息”“正在获取播放源”“缓冲中”。
- **测试**：
  - 单元754/754：新增`tests/unit/playback-start.test.ts`（交接规则、续播起播三种情形与纠正、视图结果合同），降级测试新增“先换线路再降画质”；
  - 主机原生9/9：view路由与大于512 KiB的view正文；
  - 合成UI 100/100：测试适配器对视频信息回“不支持”，详情页走预读回退；
  - 打包负例11/11。
- **实现中的问题**：第一次接入后，单元测试里的伪造后端忽略起始位置却照常返回成功，会话因此等不到seek而卡住（整套测试卡了40多分钟才被发现）。改为只有声明了`startsAt`的后端才走新路径。

## 验收与证据

- 单元：
  - 预读交接：同一`bvid/part`接过、不一致时丢弃、离开详情页时关闭；
  - 续播用起始位置打开；
  - 按原因降级的顺序与次数上限；
  - 超时后新建`VodAccess`可以重连。
- 主机原生（P1-1b）：两个来源检查同时进行；叠加层带`aid/cid`时不发nav/view。
- 合成UI：保留套件全部通过；补“预读完成/未完成时按播放”“续播起播”“断网后换线路再降画质”。
- 设备：用ADR-108的Inspector方法测以下四项，与0.56.0对比：
  - 首页卡片→详情→按播放到首帧；
  - 详情页停留3 s后按播放到首帧；
  - 续播到首帧；
  - 首帧到首条弹幕。

## 设备结果（0.57.0对比0.56.0）

[证据](../design/evidence/2026-10-25-playback-start/README.md)。按“播放”到首帧的中位数：

| 场景 | 0.56.0 | 0.57.0 |
| --- | --- | --- |
| 立即按播放，无观看记录 | 9080 ms（n=4） | 9325 ms（n=2） |
| 立即按播放，续播 | 11327 ms（n=6） | **8452 ms**（n=10） |
| 详情页停留3 s后按播放 | 8318 ms（n=5） | **5329 ms**（n=4） |
| 首帧到首条弹幕 | 4417 ms（n=6） | 3701 ms（n=18） |

- **预读交接有效**：停留3 s后，“正在获取播放源”在按播放后0.8–1.0 s就出现（立即按播放为3.1–3.4 s）。
- **续播从位置起播**：首帧时位置与保存的进度一致，没有从0起播再纠正；下面“风险”第3项关闭。
- **剩余的大头**：从获取播放源到首帧还要3.5–6 s（来源检查、播放桥、prepare），留给P1-1b。
- **一次未解释的异常**：24.5 s，接近“15 s超时＋一次重试”，没有直接证据，之后15次未再出现。
- **第6项只部分生效**：
  - **开头约3 s为空是测量错误。** 脚本先等弹幕按钮读出设置，才开始记录状态文字。单独逐帧查看时，“正在读取视频信息”从0.05 s显示到3.2 s。
  - **选定来源后不显示“缓冲中”是真问题。** 播放器已创建但还没有首帧（`idle`/`preparing`/`ready`）时，原条件只认`loading`，状态行退到“已自动选择相近的可用画质 / 音轨”，一直到首帧（约4 s）。
  - **0.57.1已修正并在设备上确认**：
    - 这几个状态也算加载中，显示“缓冲中”，“正在重试”仍然优先；
    - 4次起播都依次显示“正在读取视频信息”（约0.1 s起）、“正在获取播放源”（2.6–3.1 s起）、“缓冲中”（4.4–4.8 s起）；
    - “缓冲中”在开始播放后0.1 s内消失。
  - **新发现（OPEN）**：登录状态下，开始播放后状态行立即被“正在读取账号互动状态”取代，“已自动选择相近的可用画质 / 音轨”这条说明实际上看不到了（0.57.0时它至少在缓冲期间可见）。
    - **原因**：互动状态的回调把消息直接写进存放这条说明的同一变量。
    - **0.57.2已修正并在设备上确认**：这条说明改为单独保存，状态行把它与其他提示用“ · ”并列显示，例如“缓冲中 · 已自动选择…”“已自动选择… · 账号互动状态已读取”；按暂停/继续或开始新的播放时清除，与原来一样；设备上3次自动选择画质的起播都从选定来源起一直显示到首帧后。
- **未在设备上验证**：断网时的换线路与降级、超时后的重连。

## 风险

- **预读占用账号运行时的单一私人通道。** 打开`VodAccess`会抢占正在进行的私人读取（`acquire`），这和现在播放时一样。
- **playurl有有效期。** 详情页停留很久再播放时，签名地址可能过期；交接前检查读取时间，超过5分钟就重读。
- **`PREBUFFER_MODE`在首次起播上的行为。** 0.57.0设备测量已确认点播DASH首次起播从续播位置开始（已关闭）；失败时仍退回“先准备再seek”。

# ADR-096：番剧详情产品化、一键追番、热门番剧与倍速探查v2

2026-10-23；F06/F17/R07/R09/R15、U5。接0.48.0真机结果（Z1 USER PASS；Z2见下；Z3 FAIL）。仅在`--product-season`（0.49.0）构建生效。状态：**0.49.0已签名并升级安装/启动（平台确认，不清数据）；用户Q1/Q2 PASS、Q3 FAIL、Q4见文末；0.49.1已签名并升级安装/启动（平台确认，不清数据），Q3复验USER PASS；倍速决定见[ADR-097](097-fractional-rates-device-limited.md)**（[证据](../design/evidence/2026-10-23-season-fix/README.md)）（[证据](../design/evidence/2026-10-23-season/README.md)）。

## 用户反馈与原因

- **Z3 追番**：确认面板只看得到“查询实际状态·不重发”和“确认追番一次”，无法追番；页面仍是开发测试阶段的样式。
  - 源码核实：确认面板在状态为unknown时禁用提交键，但保留“确认追番一次”的文字（面板首位的“返回详情”被产品样式隐藏）。
  - 有两处会把失败吞成unknown，原因不留痕：
    - `reconcileBangumi`在查询失败时`catch {}`；
    - 写本机写操作记录失败时，即使查询成功也返回unknown。
  - 面板本身也是`catch {}`。所以在真机上无法区分是登录、网络还是写操作记录问题。
  - 匿名核对：季详情响应仍带`user_status.login/follow`，排除了字段缺失这一假设。
  - 番剧详情本身是W04开发工作区：每页4集、“刷新详情·只读”、分组翻页键；从番剧影视的卡片进入还要多经过一个只有“查看选集与播放”的中间面板。
- **番剧影视标签**：用户更正，页面里是“我的追番”和“我的追剧”两个不同标签，并无重复。关注页同样有这两个标签，本轮不动。用户建议增加推荐番剧。
- **Z2 倍速探查**（HTML video播生产环回MPD）：
  - 0.5×、0.75×通过；1×斜率0.81，1.25×为0.9，1.5×为1.05，均判off。
  - 不论设定多少，实际推进都在每秒0.8–1.05秒左右，更像数据供给跟不上，而不是倍速本身无效。旧探查只在窗口末尾检查是否卡住，没有统计中途的waiting。
  - 用户要求提供0.25×和2×。

## 决定

- **番剧详情产品页**（`product-season.ts`，旧变体仍用W04工作区）：
  - 封面（季详情响应里的`cover`，仅TS解析，Worker边界严格校验）、标题、更新状态、四行简介，以及“简介全文”（与视频详情共用`full-text.ts`）。
  - 主按钮“播放 · 第一集可播剧集”；分组标签；所有剧集一行横排（最多500），播放前仍由私有源Worker重新核对权益。
  - 番剧影视卡片直接打开此页，不再经过中间面板。
- **一键追番**：
  - 详情页“追番 / 已追番 ✓”按一次即提交一次。沿用F11合同（ADR-080）：持久意图、单次提交、回读为准、不自动重试。
  - 状态unknown时按钮变为“查询追番状态”，按下只查询不提交。
  - 取消二次确认面板：这是可逆操作，与点赞、关注、稍后再看一致。
  - `pgcFollows.issue()`给出固定原因：登录失效、网络、本机写操作记录无法更新、B站未返回本人状态、被拒绝、上次结果未确认。页面显示对应中文说明，并记入脱敏诊断（新增`pgc`区，只有固定代码）。
- **热门番剧**：
  - 番剧影视第一个标签，游客也可用。
  - 来源是公开番剧排行`/pgc/web/rank/list?day=3&season_type=1`，页面标明“不是个性化推荐”。最多100条，每页20；无编号或无标题的行跳过；封面只走hdslb白名单。
  - 原生`catalog`模块新增这一条固定只读路由，无调用方输入。重链接到新目录`build/catalog-pgc`（`tools/link-catalog.py --out`），冻结的`build/catalog`与旧包不变；只有0.49.0从新目录打包，并要求包含该路由。
- **倍速探查v2**：
  - 顺序改为1×先测（缓冲新鲜），增加0.25×与2×。
  - 每档先稳定2秒，再测6秒；统计窗口内waiting次数和缓冲余量。出现waiting记为stalled，但仍显示斜率。
  - 生产倍速菜单不变。是否采用“0.25/0.5/0.75×走HTML video、1×/2×走AVPlay”的混合方案，等v2真机结果再定。

## 证据

单元`tests/unit/pgc-season-product.test.ts`；原生`tests/native/catalog.test.py`；合成UI`tests/product-season-ui/season.spec.ts`（对冻结0.48.0全部失败）；汇总见[证据](../design/evidence/2026-10-23-season/README.md)。真机需复验：番剧详情与追番（含失败原因文字）、热门番剧、倍速探查v2。

## 0.49.0真机结果与0.49.1修正（2026-10-23）

- **Q1、Q2 USER PASS**。
- **Q3 FAIL**：按钮始终是“追番”；按下后提示“取消追番”，按钮仍是“追番”。
  - 源码核实：提交后无论想追还是想取消，只要回读是“未追番”，页面就写“已取消追番”，措辞错误。写入的实际结果（B站受理或拒绝）也被丢弃。
  - 回读来自季详情`pgc/view/web/season`的`user_status`，这是缓存的内容接口，写入后可能不变。
  - 本机无法区分“B站拒绝了写入”和“回读滞后”。
  - 0.49.1（`--product-season-fix`）修正：
    - 追番状态改读B站专用的本人状态接口`pgc/view/web/season/user/status`。原生`pgc-follow`只改这一条只读路由，重链接到`build/pgc-follow-status`；冻结模块与旧包不变。TS同时接受两种响应形态，旧模块仍可用。
    - 打开番剧详情时先读一次本人状态，不再沿用季详情里的缓存标记。
    - 写入被拒时，保留并显示B站的整数代码（“B站拒绝了这次追番（代码 N），未重复提交”）。
    - 受理但回读未变时，不显示成功，而显示“B站已受理…但回读的状态仍为…”，按钮变为“查询追番状态”，下一次只查询。
    - 诊断新增`follow_write_rejected`与`follow_readback_mismatch`。
- **Q4 倍速探查v2**：
  - 0.25×斜率0（等待0次，缓冲19.9秒）。
  - 0.5×紧接其后斜率0（等待0次，缓冲19.9秒）。
  - 1.25×为1.09（等待0次，缓冲29.3秒），1.5×为1.17（等待0次，缓冲32.3秒），2×为0.85（等待0次，缓冲27.2秒）。
  - 1×与0.75×未报告为off。
  - 结论（更正上文“像是数据供给跟不上”）：快档没有等待、缓冲充足，限制不在数据供给，而在本机video元素的解码/渲染，约1.1–1.2×封顶，2×反而下降。0.25×会让媒体时间停住；0.5×紧随其后仍停住，第一轮从正常状态起测时0.5×、0.75×均通过。
  - 本机可用组合为：HTML video的0.5×/0.75×加AVPlay的1×/2×。0.25×与1.25×/1.5×在本机不可用。用户决定不做混合方案，见[ADR-097](097-fractional-rates-device-limited.md)。

# ADR-111：列表逐卡容错与未知时长

2026-10-25；F02/F03/F05/F06/F07、R03、可靠性。接2026-10-25 review与ADR-108。状态：**用户确认全部4项决定（2026-10-25）；在0.58.0实现并已签名安装；设备上冷启动20次，“为你推荐”0次失败（修复前19次中2次），见[设备证据](../design/evidence/2026-10-25-list-tolerance/README.md)**。改动方案见[列表容错方案](../plans/2026-10-25-list-item-tolerance-plan.md)。

## 背景

0.57.x设备测量期间，首页“为你推荐”在启动后多次显示“内容暂时无法加载”，按“重试”后正常。

在电视上复现并定位（重载页面模拟冷启动，每次立即选择账号）：

- **复现率**：有记录的19次重载中2次（约11%）；此外0.56.0与0.57.2调试启动后各自然出现一次。（原写“27次中3次”，是重复计数，已更正。）
- **失败帧**：账号内核Worker返回`recommendations-read → error / invalid / recommend.invalid`。HTTP请求本身正常完成，与成功时同样约630 ms。
- **抛错位置**：在Worker里`parseRecommendationCard`抛错处暂停，只读字段的类型、长度与格式标志（不读内容）。只有一项不合格：`durationSeconds`为**166242 s（约46小时）**，超过校验上限86400 s；其余字段全部合格。
- **为什么重试能好**：推荐流每次返回不同内容，所以重试多半能避开那张卡。

这暴露出两个更普遍的问题。

1. **一张卡不合格，整个列表失败。**

   | 解析器 | 现状 |
   | --- | --- |
   | 推荐（`recommendations.ts`） | 任一视频卡不合格就抛错，整批作废；非视频卡跳过并计入`omitted` |
   | 热门（`popular.ts`） | 任一行不合格就抛错 |
   | 排行与分区排行（`parseRankingBody`） | 任一行不合格就抛错 |
   | 视频搜索（`search.ts`） | 任一行不合格就抛错；时长超过24 h也抛错 |
   | 用户搜索（`user-search.ts`） | 一位用户的预览视频不合格，整页失败（预览本来是可选的） |
   | 番剧搜索、热搜、稍后再看、历史、收藏内容、关注动态、追番 | 任一行不合格就抛错 |
   | UP投稿（`parseUpArchivesBody`）、番剧排行 | 已经跳过不合格行，但不计数 |

   不合格的原因可能很平常：标题里有控制字符、UP名为空、同一视频出现两次、时长超出上限，都会让整页“暂时无法加载”。

2. **时长超出上限就拒绝。**
   - 列表卡片的时长上限是24 h：推荐、热门、排行、UP投稿、搜索都是86400 s。超过24 h的视频（例如长时间直播的回放）确实存在。
   - 卡片上的时长只是展示信息，不应该让卡片乃至整个列表作废。
   - UP投稿已经把超出范围的时长当作0；另有几处打开视频时也用0占位（`product-home.ts`、`product-library.ts`、`product-following.ts`）。
   - 但卡片渲染没有处理0：`clockTime(0)`显示“0:00”，读屏文字是“0分0秒”。

## 决定

1. **列表解析逐卡容错。**
   - 适用范围：解析外部正文的列表解析器（`packages/bili-client`中、在Worker里运行的部分）。
   - 每一行单独解析，规则如下：
     - 能规范化的先规范化：去掉控制字符、截断到上限长度、超长或无效的时长记为未知；
     - 仍不合格的跳过，并计入`skipped`，不再让整页失败；
     - 重复的视频同样跳过并计数。
   - 下列情况仍然整体失败（`invalid`），因为它们说明响应格式变了，而不是个别卡片的问题：
     - 根结构、`code`、列表类型或大小不对；
     - 列表非空，但每一行都被跳过。
   - 用户搜索：预览视频不合格时，只去掉这一位用户的预览，用户本身保留。
2. **超长时长按未知显示。**
   - 未知时长沿用现有表示：卡片的时长字段为0。B站视频最短1 s，0不会和真实时长混淆。合同的字段形状与上限不变。
   - 列表解析器遇到超过上限、不是整数、负数或格式错误（搜索的“分:秒”）的时长，一律记为0，保留卡片。
   - 界面上，时长为0时不显示时长角标，读屏文字也省略时长：
     - 卡片角标（`content-card.ts`）；
     - 推荐列表、热门/游客列表、用户搜索预览、搜索结果中的时长文字。
3. **跳过的数量只进诊断。**
   - 结果里带可选的`skipped`计数（为0时省略），合同允许这一可选字段并检查范围。
   - 主线程把`skipped>0`记成“帮助与诊断”里的固定事实（新增诊断代码），不向观众显示。观众对此无能为力，显示出来只是噪音。
   - 推荐页现有的“本批N项非普通视频未展示”保持原义，不并入跳过数。
4. **Worker与主线程之间的合同保持严格。**
   - 主线程对Worker结果的再校验（`parse*Result`等）不变：其中一张卡不合格仍然整体拒绝。
   - 理由：外部正文不可信，所以逐卡容错；Worker产出的结果是自己的代码，出错就是缺陷，应该暴露而不是悄悄吞掉。
5. **超过24小时的视频能否播放，另行决定。**
   - 本ADR不改详情、播放、续播记录、弹幕与投屏的上限，涉及的位置：
     - `vod-catalog.ts`、`guest-video.ts`、`public-kernel.ts`的分P时长；
     - `local-profile.ts`、`overlay-read.ts`、`cast-receiver.ts`。
   - 已知后果：这样的视频在列表里显示为“时长未知”，但打开详情、播放仍会失败，与今天一样。这要单独出ADR并在电视上验证（AVPlay对超长DASH的处理、本机进度记录的上限）。
   - **用户决定（2026-10-26）：超过24小时的视频应能播放。** 待单独出ADR实现上述各处上限的放宽，并在电视上验证；尚未实施。

## 实现（0.58.0）

- **共用工具**（`packages/bili-client/src/list-rows.ts`）：
  - `eachRow`：逐行解析；不合格（`DomainError`）或返回空的行计入`skipped`；非空列表全部被跳过时`invalid`；其他异常照常抛出，不被吞掉；
  - `seconds`、`clockSeconds`：时长不在0–86400 s或格式不对时为0；
  - `line`：控制字符换成空格、去首尾空白、截断。
- **各列表**：
  - 推荐、热门、排行与分区排行、UP投稿、番剧排行；
  - 视频/用户/番剧搜索、热搜；
  - 稍后再看、历史、收藏内容、关注动态、追番。

  每个都改为逐行容错。资料库各列表把每一行交给合同里新导出的单卡校验（`parseWatchLaterCard`、`parseFavoriteItem`、`parseFollowUpdate`、`parsePgcFollowCard`，历史沿用`parseHistoryCard`），不合格就跳过。
- **规范化而不是拒绝的字段**：
  - 播放数不可读时为0（界面本来就不显示0）；
  - 搜索的计数不可读时为0；
  - 番剧搜索的标签与评分不可读时留空或省略；
  - 稍后再看的类型与状态不可读时为“未知”；
  - 历史的进度与时长不可读时为“未提供”。
- **翻页**：收藏内容与追番的“没有更多”按源数据的行数判断，不按保留下来的卡片数，避免跳过一行就提前结束；追番合同相应改为“保留数＋跳过数不足4”。
- **热搜**：名次保持源数据的值，不重新编号。名次无效或不大于上一个保留项的行跳过，保留下来的名次仍然严格递增（与方案“重新编号”不同，更简单，合同不变）。
- **跳过数的传递**：
  - 各结果、页或批次带可选的`skipped`；
  - 合同用`skippedCount`检查：正整数，保留数＋跳过数不超过源行数，只出现在成功结果里。
- **诊断**：
  - 常驻内核客户端收到结果、以及追番读取完成时，看到`skipped>0`就记一条固定事实`app/list_items_skipped`；
  - 只记事实，不记数量与内容。
- **时长显示**：时长为0时以下位置不显示时长，读屏也不读：
  - 卡片角标（`durationText`）；
  - 推荐列表、热门/游客列表、用户搜索预览、搜索结果的文字。
- **测试**：
  - 单元761/761：新增`tests/unit/list-tolerance.test.ts`，含166242 s推荐卡回归；11个测试文件里“一行不合格就整体拒绝”的断言改为新规则，“全部不合格仍拒绝”与合同层的严格断言保留；
  - 合成UI新增`unknown-duration.spec.ts`；
  - 打包负例11/11；
  - 原生C未改，主机原生测试沿用。

## 设备结果（0.58.0）

- **冷启动**：20次全部正常，推荐结果均为`ok`，没有`invalid`；修复前有记录的19次重载中2次失败。
- **时长未知**：第4次首行出现1张时长按未知显示的卡片，说明这条显示路径在设备上生效。源数据没有记录，不能确定源时长是超过24 h还是正好为0。
- **统计局限**：按约11%的失败率，连续20次不失败的概率约10%。修复的主要依据是机制：已定位字段，并有单元回归。
- **未见到**：这20次没有发生跳过，所以`list_items_skipped`诊断事实没有在设备上见到；其他列表也没有在设备上专门制造坏行。

## 不做

- 直播搜索：直播不在当前交付范围（ADR-068），代码保持不动。
- 放宽合同里的时长上限，或把时长改成可空字段（历史记录已有的`null`表示保持不变）。
- 在界面上提示“有N张卡未显示”。

## 验收与证据

- **单元**：
  - 每个列表解析器：一行不合格（含控制字符、空UP名、重复、超长时长、时长格式错误）时，其余行保留，`skipped`计数正确；
  - 全部行不合格时整体`invalid`；
  - 推荐用166242 s的卡片做回归；
  - 现有“一行不合格就整体拒绝”的断言改为新规则；
  - 合同层“Worker结果中一张卡不合格就拒绝”的断言保留。
- **合成UI**：时长为0的卡片不显示角标、读屏不读时长；保留套件全部通过。
- **设备**：
  - 用定位时的方法重复冷启动20次，“为你推荐”不再出现`invalid`；
  - 诊断事实在出现跳过时可见。

## 风险

- **掩盖格式变化。** 如果B站改了某个字段的格式，逐卡跳过会让列表变短，而不是报错。由“全部行不合格仍整体失败”和诊断计数兜底。
- **时长0的旧用法。** 续播判断`timeMs < durationSec*1000`（`product-search.ts`）在时长为0时不提示续播，这与今天UP投稿卡的行为相同。本ADR不改。

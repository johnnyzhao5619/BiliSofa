# ADR-117：全站排行登录时走本人会话，被拒时显示风控并暂停，首页各行依次读取

2026-10-26；F02/F03、R05、性能与交互。接0.64.1设备调查与ADR-105/106/108/116。状态：**用户已确认全部决定（2026-10-26）；0.65.0已签名安装，设备验证通过（登录与游客的排行榜读取、方向键响应）；0.65.1清理已签名安装**。改动方案见[P2b排行榜修复方案](../archive/2026-10-26-plans/2026-10-26-p2b-ranking-fix-plan.md)。

## 背景：0.64.1排行榜失败的调查

调查方法：
- 用调试方式冷启动两次，用[kernelwatch.mjs](../design/evidence/2026-10-26-p2b-device/kernelwatch.mjs)观察Worker消息，不扣住任何请求；
- 只记录时刻、操作名、结果类别与API码。

**“加载一分多钟后`timeout`”是测试脚本造成的**：
- 首页各行要等焦点进到上一行才开始读取：排行榜等“热门视频”，热门视频等“为你推荐”。冷启动后焦点在最上面的“继续观看”，所以下面几行的骨架卡一直在，但读取根本没开始。
- 0.64.1第二次复测时，[holdcheck.mjs](../design/evidence/2026-10-26-p2b-device/holdcheck.mjs)扣住含ranking的消息，一直没放开。焦点后来进到“热门视频”，排行榜请求才发出，正好被扣住。公共内核12秒请求预算到期，报`timeout`并重建Worker。
- 当时“扣住的读取为0”，只是请求还没发出。

**不扣请求时，实际原因是风控拒绝**：

| 读取 | 发出到结果 | 结果 |
| --- | --- | --- |
| 全站排行（公共内核，匿名，不带cookie） | 0.31 s、0.64 s | API -352，页面显示“内容暂时无法加载”，代码`network` |
| 分区1005（登录，账号内核本人会话，ADR-105） | 1.02 s | 成功，8张卡 |

同一时段从同一网络的Mac对照：

| 请求 | 结果 |
| --- | --- |
| 全站排行：匿名 / 带访客cookie / WBI签名 / WBI＋访客cookie | 全部-352 |
| 分区排行（rid=1005），同上四种 | 全部-352 |
| 热门视频（匿名） | 0 |

这说明三件事：
- 这个出口目前拒绝匿名排行榜请求，访客标识（ADR-106）和WBI签名都不起作用；
- 登录会话下同一接口能读；
- 分区排行登录后已走本人会话（ADR-105），而全站排行即使登录也只走匿名通道，所以登录后一直失败。

另有两处缺口：
- 首页货架把-352显示成通用的“内容暂时无法加载”，没有ADR-105的风控说明；
- 全站排行不经ADR-105的节奏，被拒后也不暂停。

## 决定

### 1. 登录时全站排行走本人会话

- **账号内核新增固定只读路由**：`account-read-kernel.c`新增`ACCOUNT_RANKING`（11）。
  - 输入只能是`all`；
  - URL固定为`https://api.bilibili.com/x/web-interface/ranking/v2?rid=0&type=all`，Referer为B站首页；
  - 会话、cookie、正文/头部上限、TLS、不跟随重定向与`ACCOUNT_CATEGORY`完全相同；
  - 不接受调用方URL，不新增写操作。
- **合同**：`PublicReadCommand`加`{kind:'ranking'}`，结果加`{kind:'ranking', items}`，条目校验与分区相同；非0 API码为`refused`。
- **页面**：首页货架与“查看更多”网格都拿到本人会话的排行读取；有活动账号时用它，否则走公共内核匿名读取。
- **游客**：照旧匿名，不加访客标识和WBI（对照显示无效）。

### 2. 全站排行纳入ADR-105的节奏，被拒时说清楚

- 经`pacedRead`读取，列表类型`ranking`：
  - 10分钟进程内复用，取代原公共通道的5分钟复用；
  - 风控拒绝（API -352/-412/-509/-799或HTTP 412）后与分区、UP投稿共用60秒暂停，期间不发请求。实现时改为同一通道（游客或账号）内共用，见“实现”。
- “刷新”清除这份复用，但仍受暂停约束。
- 首页货架与网格失败时：
  - 风控显示`limitedText`：“B站暂时限制了访问（风控 -352），约 N 秒后可重试”，游客另加“；登录后通常更稳定”；
  - 其他失败照旧。
- 暂停期间按“重试”不发请求，只更新剩余秒数。
- 有快照的行照旧保留快照并显示“显示的是上次的内容”，原因代码放在状态的`title`。
- “帮助与诊断”写“最近一次全站排行读取：账号会话/游客 · 成功/B站返回 -352”。

### 3. 首页各行依次读取，不等焦点

- 进首页先读第一行（ADR-116不变）。之后一行读完（成功或失败）就开始下一行，按“为你推荐 → 热门视频 → 排行榜”的顺序，一次一行，不并行。
- 焦点先到达某行上方时，那一行仍可提前开始；正在读或已读完的行不重复读取。
- 不自动重试失败的行。每次进入首页每行最多读一次；5分钟内返回首页沿用运行内复用（ADR-116）。
- 封面照旧在接近可视区域时才加载（`CoverArt`的300 px预取范围），屏幕下方的行不会提前拉封面。
- 本条取代ADR-091“焦点到上一行才读下一行”的规则，其余货架规则不变。

## 实现（0.65.0）

按决定实现：
- 账号内核新路由`ACCOUNT_RANKING`（11）与Worker映射；
- 合同新命令与结果；
- `signedPublicReads.ranking`；
- 全站排行经`pacedRead`，首页货架与网格都拿到本人会话；
- 货架风控文字；
- 各行依次读取。

实现中补的几处：
- **暂停按通道分开**：测试发现，“谁在观看”下面已挂着一个游客首页（电视上也一样：0.64.1观察记录里，选账号时停掉了一个进行中的公共读取）。依次读取后，这个游客首页会匿名读全站排行，得到-352。若暂停全局共用，选账号后的本人会话读取也会被这60秒挡住。所以暂停改为游客、账号各自一份：同一通道里分区、UP投稿、全站排行仍共用；游客被拒不再挡住本人会话。这改动了ADR-105“所有读取共用暂停”的一点。
- **被页面盖住时不接着读**：首页上有任何页面（如“谁在观看”、详情）时，读完一行不自动开始下一行；回到首页、焦点进入某行时照旧开始它的下一行。这样“谁在观看”下的游客首页只读第一行，不再替被丢弃的页面发请求。
- **行尾追加进同一队列**：热门行尾多读一页原本与行读取并行，会取消正在读的下一行（共用同一读取对象）；现在排在同一队列里。
- **测试用的public-read通道**：合成UI经旧的`public-read`单次Worker模拟账号内核，因此`public-read.c`加操作6（输入`all`，同一固定URL），`public-native-api.ts`、`public-read-worker.ts`与合成fixture同步。产品包不含这个模块。
- 打包检查要求账号内核WASM里有`ranking/v2?rid=0&type=all`。

结果：
- 原生主机：账号内核5/5（新路由的固定URL与Referer，6种非法输入不进cURL，退役操作号改为12）；public-read 10/10（操作6的路径与非法输入）。
- 单元/合同785/785（新增：全站排行走本人会话且不碰匿名内核、刷新清除复用、游客被拒后暂停且刷新与分区都不发请求、暂停按通道分开、命令与结果的解析）。`visitor-id.test.ts`里“游客被拒后账号也被挡”一处改为按通道的新行为。
- 合成UI 120/120：
  - 新增`tests/product-up-fix2-ui/ranking.spec.ts`共3条：登录不动焦点各行依次读、排行榜走本人会话且网格复用；登录被拒显示风控与秒数、重试不发请求；游客匿名读、被拒提示登录。
  - 去掉依次读取后，前两条失败；游客那条仍通过（游客焦点本就落在热门，会照旧触发下一行）。
  - `fix2.spec.ts`两条改为先等首页排行榜读完，被拒那条的“帮助与诊断”改为全站排行。
- 包：0.65.0未签名WGT `9b3f89e5…c82d`，负例11/11。

## 设备验证（0.65.0）

签名`f83e83e5…f84c`，升级安装/启动platformSuccess（不清数据）。详见[设备证据](../design/evidence/2026-10-26-p2b-device/README.md)“0.65.0设备验证”。

- **登录**（×3，不移动焦点）：
  - 三行依次读取：为你推荐 → 热门视频 → 排行榜，按OK后3.9–4.6 s全部读完；
  - 排行榜走本人会话，0.70–0.75 s读出12张卡。“风险”第一条的推断成立。
- **游客**（×3）：
  - 匿名全站排行仍是-352（0.30–0.33 s）；有快照时保留快照并标“显示的是上次的内容”；
  - 无快照时显示“B站暂时限制了访问（风控 -352），约 60 秒后可重试；登录后通常更稳定”，5 s后按重试只更新秒数，不发请求；
  - “谁在观看”下的游客首页只读了第一行，选账号时被停掉。
- **方向键**（ADR-114同法，与安装前的0.64.1对比）：
  - 快：中位数38对35 ms，最大76对67 ms，每轮>50 ms帧2.0对4.0；
  - 慢：中位数33对31 ms，最大42对61 ms，每轮>50 ms帧1.3对2.7；
  - 都没有超过200 ms的按键；
  - 条件不完全相同：0.64.1的热门行停在8张卡的快照上，0.65.0已刷新为12张卡；
  - 测量在三行读完之后开始，不覆盖读取进行中按键的情况。


## 0.65.1清理

- 全站排行的匿名通道去掉原来的5分钟复用：`KernelRanking`改为普通通道，与分区通道相同。复用与暂停只由外层的节奏读取负责；“刷新”只清除那一份复用。
- 删除没有调用方的代码：`identityRuntime`（身份核对已走账号内核，ADR-109）、`categoryLabel`、`interactionRelation`和`SignedPublicReads`类型。直播相关的未用入口按ADR-068保留。
- 行为不变：
  - 单元785/785、合成UI 120/120、包负例通过；
  - 未签名`dd778893…b783`，签名`16e6a879…f878`（证书预检PASS，配置只改版本号）；
  - 已升级安装/启动（不清数据）；新调试启动确认版本0.65.1，登录时排行榜走本人会话0.71 s读出12张卡（[记录](../design/evidence/2026-10-26-p2b-device/0.65.0/kw-0.65.1-account.txt)）。


## 不做

- 不给匿名排行加WBI、访客标识或浏览器指纹参数；不使用其他客户端的密钥。
- 不自动重试，不缩短60秒暂停。
- 分区横排仍只是入口，不在首页预读分区。

## 验收与证据

- **原生主机测试**`tests/native/account-read-kernel.test.py`：
  - `ACCOUNT_RANKING`只接受`all`，URL与Referer固定；
  - 空串、`0`、数字、`all|x`、CR/LF等非法输入都不进入cURL；
  - 原有路由不变。
- **单元测试**：
  - 合同：新命令与结果的解析与拒绝；
  - `pacedRead`：`ranking`的复用、清除复用、暂停与诊断文字。
- **合成UI**：
  1. 有活动账号时，首页排行榜与网格走本人会话；
  2. 游客被拒时显示风控提示与秒数，暂停期间按“重试”不发请求；
  3. 不移动焦点，三行依次读完，同一时刻最多一个读取在进行；
  4. 有快照的行被拒时保留快照。
- **设备**（需签名安装授权）：
  - 用kernelwatch.mjs同法观察登录与游客两种状态；
  - 按ADR-114同法测首页连续方向键的响应，与0.64.1对比。

## 风险

- 登录会话下全站排行能读，实现前只是推断（同一接口的分区rid=1005在电视上成功）；0.65.0设备验证已确认rid=0在登录状态下能读出。
- 风控随出口变化，这次结果不证明以后不会再变。
- 进首页后多出最多两次读取（热门、排行榜）。它们仍走现有内核和节奏，设备上按键响应与0.64.1相当。

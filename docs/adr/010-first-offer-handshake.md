# ADR-010：一次电视预授权与首次源设置握手

日期：2026-10-16。状态：W01/F06/F20内部0.0.47候选，实际手机效果待验收。承接ADR-009，原先电视后确认入口与发现/自动回跳入口保留，不改变完整v1.0.0/F01–F20范围。

## 证据与问题

0.0.46多轮手机时间全零，即使TV与手机均134秒，或手机3:43与TV222.1秒。强行停止Android官方App后依旧全零。新源重投报告receiver_v2_1a0ca225含source_changed、Stop接受与locked拒绝，无uri_accepted；非零时长/位置/生成元数据的完整socket写入已取得。它证明了第一次源设置失败、电视另行播放、第二次刷新源又被拒绝的握手顺序缺口；不能直接把所有全零或约53秒停止都归因于此。

官方公开Android9.15.0包的设置源成功回调会登记当前视频，位置消费存在当前视频类型前提；存在其他setter，不宣称唯一登记入口。用户实际9.12.0效果仍待设备验证。详见research/2026-10-16-official-cast-zero-time.md。不复制官方代码、身份或opaque元数据。

## 决策

新增独立电视入口“允许一次官方投屏并播放”。遥控器确认该按钮，即明确允许本监听窗口中首个合规来源检查并自动起播。CastProbeRequest可携带唯一可选字段receiverApproval:'next-source'；字段缺失保持原先先拒绝、TV另确认模式。它由受控本地UI生成，经scope和严格DTO验证，不是网络发送端能授予的权限。startup/自动回跳入口不能使用该选项。

首个请求仍须通过原4096字节有界XML、必须字段唯一、目的地/路径/格式/期限校验，才绑定单一TCP IPv4对端和精确原URI并对SetAVTransportURI返回200。这个成功表示已接受当前资源意图，不表示TLS检查、SDK准备或声画成功。在源HTTPS/CA/206范围/MP4文件头检查完成之前，媒体桥不能启动，UI不调用AVPlay。

已授权且正在检查/首次准备的查询为TRANSITIONING，未知时间/时长诚实为零；现有30秒启动意图窗口内Play仅幂等确认，不重复调用SDK，不伪报PLAYING。源检查PASS后UI按先前电视授权自动启动一次已检查候选，不要求手机重投或第二次电视确认。随后只有真实递增播放器快照能给出播放/进度/时长。

任何其他对端、不同URI（包含query刷新）仍拒绝，不把同视频相似地址当相同批准源。首次源检查失败立即撤销早期receiver；一次候选已消耗，失败后新请求不能在本轮悄悄获得新授权。Back/Home、旧scope、错误、停止和租期沿用原清理。更换视频须Back后重新允许；UI明确提示。Stop关闭当前解码器但保留原有界租期；重放与控制权接管策略按ADR-009。

## 边界与恢复

SSDP监听仍最长5分钟，源检查最多8秒，原生媒体桥最长3分钟/签名期限，receiver控制期限最多180秒从首源接受算，不因源检查或重试延长；两者起算点不同，控制可先于媒体结束。原候选60秒确认期限、原生字节/连接/窗口预算、主机/路径/TLS/CA限制全部保留；不新增权限、端口、外部服务、业务写操作、音量控制、GENA或第三方身份。新选项不扩展SOAP64位/receiver32位事实和178进度预算；用既有approved/uri_accepted/真实查询事实取证。

SetAVTransportURI与Play是不同动作，依据[UPnP AVTransport:1 §§2.4.1、2.4.9及6.1](https://upnp.org/specs/av/UPnP-av-AVTransport-v1-Service.pdf)。电视预授权/一次源/未检查前准备意图应答是本项目内部策略，不宣称UPnP认证或Bilibili公开协议承诺。

## 验证

新增实际打包Worker+UI的首源应答/准备期Play与TRANSITIONING/自动起播单次SDK调用；TLS失败不触达播放器且不重新授权；Back后晚到源成功不播放；陌生对端与刷新URI仍拒绝。夹具只在首次200后继续发送播放命令，以覆盖此前“首次500但脚本无条件继续控制”的测试盲点。原入口仍测试首次500/TV确认，避免把两种授权时序混为同一种流程。所有夹具及本地检查与官方9.12.0真机时间显示分别记录。

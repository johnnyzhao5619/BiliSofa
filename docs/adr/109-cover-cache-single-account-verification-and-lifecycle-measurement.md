# ADR-109：封面跨页保留、账号身份只核对一次、生命周期先测再改

2026-10-25；F01/F02/F12、性能。接ADR-108与0.54.0设备对比。状态：**用户确认全部3项决定（2026-10-25）；P0-3a在0.56.0实现，已签名并升级安装；设备对比完成，后台恢复一项未能测量**（[设备证据](../design/evidence/2026-10-25-lifecycle/README.md)）。改动方案见[P0-3方案](../plans/2026-10-25-p0-3-lifecycle-plan.md)。

## 背景

原review的P0-3（页面保活、后台恢复、关闭超时、启动顺序）是在ADR-108之前写的。按现在的代码重新核对：

- **已被ADR-108解决或大幅缓解的：**
  - 公开列表的快照与缓存是应用级的，切页、返回、换身份后都还在，所以重建页面时不再等网络；
  - 冷启动时游客首页读到的热门第一批，选择账号后由账号首页直接复用（同一批次缓存），不再是浪费的请求；
  - 列表页关闭不再等待原生关闭：取消只停当前传输，“请重新打开应用”在列表页基本不会再出现（播放器仍可能出现，归P1）。
- **仍然存在的：**
  - **封面每次切页都重新下载。** `cover-art.ts`的`trim()`在没有任何页面持有封面时清空全部缓存（第8行），而切页时旧页先关闭、新页后挂载，所以每次切页都会全部清空。另外最多只缓存48张，并发只有2路。
  - **选择账号到推荐首卡仍需约4.2 s**（0.54.0实测，与0.51.3相同）。顺序是：身份Worker启动一个WASM实例、导入jar、跑nav核对身份 → 首页重建 → 账号内核再启动一个WASM实例、再导入jar、再跑一次nav → 推荐。同一个jar的nav跑了两次，WASM也启动了两次。
  - **后台恢复与返回上一页的实际耗时没有测过。** 页面DOM保活改动面大（各页面都假设owner的生命周期等于可见期），是否还值得做，要先看封面与缓存修好后的实测。
- **不改的约束：**
  - ADR-099：冷启动必须先选择“谁在观看”，不自动进入上次账号；
  - ADR-027：从后台恢复时，先在前台重新核对身份，再恢复交互；隐藏期间不保留原生会话。

## 决定

### 1. 封面缓存跨页保留

- 去掉“没有页面持有就全部清空”的规则。空闲封面按LRU保留：最多160张、24 MB、10分钟。正在显示的封面不受上限影响。
- 并发从2路提高到4路（两个内核复用连接后，封面是剩下的主要并行请求）。
- 尺寸、类型、像素上限，以及重新编码为有界JPEG的规则都不变。
- 设置 → 清除读取缓存时一并清空。

### 2. 账号身份由账号内核核对，只核对一次

- 账号内核新增“身份”请求。它就是会话打开时本来就要跑的那次nav，结果按身份Worker现有的解析器（`parseAccountIdentity`）返回`uid`、名称与资料。
- `accountRuntime.verify`改走账号内核：核对通过后，同一个会话直接被推荐等私人读取复用，不再启动身份Worker。
- 选择页显示时预热账号内核：只编译WASM，不导入jar、不发请求。这样不违反ADR-099“选择前不读取任何私人内容”。
- 身份Worker只保留扫码登录（`login`）。会话更新、移除账号等流程不变。
- 安全规则不变：mid必须与账号一致，`isLogin`必须为真，cookie只在内核Worker内。

### 3. 生命周期先测再改

在0.55.x上用ADR-108的Inspector方法测以下四项：
- 从Home键回到应用到首页可操作；
- 从详情页、UP主页返回列表；
- 在顶层页之间切换；
- 切换账号。

结果决定是否在P0-3b做以下两件事（届时另立ADR或补充本ADR）：
- 顶层页面DOM保活；
- 后台恢复时保留同一账号的列表快照（只在内存中，jar仍随隐藏关闭）。

## 不做

- 不自动进入上次账号（ADR-099）。
- 不在隐藏期间保留原生会话或jar（ADR-027、ADR-108）。
- 不做持久化列表快照（冷启动先画上次首页）：涉及存储结构与私人数据落盘，单独决定。
- 不改播放链路（P1）。

## P0-3a实现（0.56.0）

- **封面**：`cover-art.ts`去掉“无引用即全部清空”。空闲LRU上限160张、24 MB、10分钟，并发4路；新增`clearCovers()`，设置 → 清除读取缓存时调用。
- **身份**：
  - 账号内核新增`identity-verify`请求：总是跑一次nav，按身份Worker的分类返回结果（-101登录失效、-403权限、其他拒绝为网络、`isLogin`为假或mid不符为登录失效），身份用同一个`parseAccountIdentity`＋`navAccountProfile`解析；
  - 核对通过后，会话标记为已核对，之后的私人读取在10分钟内不再跑nav；
  - `accountRuntime.verify`改走这个请求，账号运行时不再创建身份Worker；
  - 身份Worker仍随包，只供扫码登录。
- **预热**：有已保存账号时，“谁在观看”出现的同时启动一个账号内核，只编译WASM，不导入jar、不发请求；被选中的账号沿用它。应用隐藏时丢弃。
- **测试**：
  - 单元750/750：账号内核Worker的身份规则（成功、每次都重核、-403、-101、`isLogin`为假、其他拒绝）；`verify`走内核且之后的读取复用同一内核；预热不发请求并被选中账号沿用；
  - 封面合成规格改为“空闲封面跨视图保留、`clearCovers`全部释放、并发不超过4”；
  - 合成UI的测试适配器把`identity-verify`转给身份Worker及其现有夹具。

## 设备结果（0.56.0）

与已安装0.54.0同步骤对比，每项测一次，详见[设备证据](../design/evidence/2026-10-25-lifecycle/README.md)：

- **选择账号到推荐首卡**：4533→2619 ms，新Worker 2→0。游客→重新选择账号这条路径不经过选择页、没有预热：4485→2789 ms。
- **首页→搜索→首页**：第一行封面全部出现518→181 ms，重新下载的封面4→0张。
- **返回**：从详情页522→241 ms，从UP主页经详情返回1018→513 ms，都不再重新下载封面。
- **顶层切页**：到搜索334→127 ms；到“我的”181→296 ms，单次测量，可能是波动。
- **后台恢复**：两个版本都没能测到。应用在后台时JavaScript暂停，而按Home后开发机与电视的sdb连接会断开。仍OPEN。

**对第3节的结论**：返回与切页已降到0.1–0.5 s且不发网络请求，DOM保活收益很小，建议不做。P0-3b只保留后台恢复，等有不依赖调试连接的测量方法（例如“帮助与诊断”显示应用自己记录的恢复耗时）再决定。

## 验收与证据

- 单元：
  - 封面LRU的上限、TTL，以及跨“页面关闭→新页面挂载”的保留；
  - `verify`走账号内核，nav身份不符、登录失效、换账号的规则；
  - 预热时不导入jar、不发请求。
- 合成UI：保留套件全部通过；选择页与登录状态相关的规格不改变断言。
- 设备：
  - 选择账号到推荐首卡（0.54.0基线4203 ms）；
  - 切页往返后的封面是否立即出现（不再重新下载）；
  - 第3节的四项测量。

## 风险

- **身份核对改走另一个Worker。** 身份Worker的nav解析与失败分类要逐项对齐，否则会把网络失败误判为登录失效（或反过来）。实现时复用同一解析器，并把身份Worker现有的单元测试全部改为对内核运行。
- **封面缓存变大后的内存。** 24 MB上限在电视上是否合适，以设备上的播放内存门槛为准。

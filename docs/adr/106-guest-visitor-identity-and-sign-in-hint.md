# ADR-106：游客读取分区与UP投稿时带B站官方访客标识（本机保存、可清除），被拦时提示登录

2026-10-23；F02/F04、R04/R05、U5。接0.51.2真机结果与游客对照实验。用户确认方案（访客标识本机保存、可在设置中清除；被拦时提示登录更稳定；WBI暂不加）。仅在`--product-up-fix3`（0.51.3）构建生效。状态：**0.51.3已签名并升级安装/启动（平台确认，不清数据）；游客V1g、清除访客标识、登录状态回归 USER PASS**（[证据](../design/evidence/2026-10-23-up-fix3/README.md)）。

## 背景

- 0.51.2登录状态的分区与UP投稿 USER PASS（ADR-105）；游客走匿名catalog通道，请求不带任何cookie，真机未验证。
- 浏览器第一次访问B站时，会从`x/frontend/finger/spi`拿到`buvid3`/`buvid4`，之后每个请求都带上它们（以及`b_nut`）；官方客户端也有自己的设备标识。匿名请求完全不带标识，是它与正常访客最明显的区别。
- 限时对照实验（6个请求、间隔约10秒：基线、spi、带访客cookie、nav、WBI、UP+cookie）当时全部code 0，风控宽松时段无法区分哪一项起作用。用户决定先加访客标识，WBI暂不加。

## 决定

- **原生入口`catalog-visitor.c`**：原样包含冻结的`catalog-ua.c`（其下`catalog-up.c`、`catalog.c`、`probe-guest.h`也不变），链接到新目录`build/catalog-visitor`。只新增两件事：
  - 固定路由`visitor-id`：GET `https://api.bilibili.com/x/frontend/finger/spi`（Referer为B站首页），本身不带任何cookie；若同时传入访客标识则拒绝。
  - 可选的首个参数`--visitor=<buvid3>|<buvid4>|<b_nut>`：buvid3为16–64个`[A-Za-z0-9-]`，buvid4为16–128个`[A-Za-z0-9%-]`（已URL编码），b_nut为10位数字；校验通过后作为这次请求唯一的`Cookie: buvid3=…; buvid4=…; b_nut=…`，否则不进入cURL。
  - TLS、正文/头部上限、不跟随重定向、固定路由表等全部沿用。
- **合同与Worker**：
  - 新操作`public-visitor`（独立父操作，取消不会波及其他通道），结果只带`b3`、`b4`；Worker里解析spi正文，原始正文与`Set-Cookie`不出Worker。
  - 分区排行与UP投稿请求可带`visitor`字段，只在本构建接受，结果中从不回传；其他操作带此字段一律拒绝。
- **本机保存**：
  - 普通存储键`bilisofa.visitor.v1`，内容只有`{version, b3, b4, at}`，与登录会话分开；30天内复用，过期或内容无效时重新获取；`b_nut`取获得时刻（秒）。
  - 只在游客读取分区或UP投稿、且不在风控暂停期间时才获取；获取失败时这次读取照旧匿名进行，10分钟内不再获取。
  - 登录时走本人会话（ADR-105），不获取、不使用访客标识。
- **设置 → 本机数据**：
  - 一行状态：“已保存在本机（30天内有效）”或“未保存，需要时自动获取”；
  - 按钮“清除B站访客标识”：一次清除，焦点留在按钮上，下次游客读取时重新获取。
- **提示**：游客读取被风控拒绝时，在原提示后加“；登录后通常更稳定”；登录状态不加。“帮助与诊断”的那一行写成“游客（带访客标识）/游客（无访客标识）”。

## 不做

- 不加WBI签名，不生成或伪造浏览器指纹参数（如`_uuid`、`buvid_fp`、`b_lsid`），不使用其他客户端的密钥或ticket，不用通用串伪装。
- 不自动重试；10分钟复用、60秒暂停保持不变。
- 访客标识不进入日志、诊断或证据；只用固定词描述是否保存、是否带上。

## 证据

- 原生主机测试`tests/native/catalog-visitor.test.py`，20条：继承`catalog`、`catalog-up`、`catalog-ua`全部检查；带访客标识时Cookie就是这三项、别无其他；`visitor-id`是固定的无cookie GET；8种非法值（空、过短、位数不对、分号注入、空格、多一段、CR/LF、在`visitor-id`上带标识）都不进入cURL。
- 单元`tests/unit/visitor-id.test.ts`，4条：spi只取b_3与URL编码后的b_4；只有分区/UP请求可带标识且不回传；30天复用、失败10分钟内不再获取、取消不计、清除后重新获取、内容无效视为未保存；游客被拒时的提示与“帮助与诊断”文字。
- 合成UI`tests/product-up-fix3-ui/fix3.spec.ts`，5条，fixture仿“无访客标识就拒绝”（分区-352、UP投稿HTTP 412）：
  1. 游客分区获取并保存访客标识后读取成功，重启后复用、不再获取；
  2. UP投稿带同一标识；
  3. 设置中清除：一次清除、焦点不丢，下次读取重新获取；
  4. 游客被拒时提示登录；
  5. 登录时不获取访客标识，被拒时不提示登录。
  - 前4条对冻结0.51.2全部失败（第5条为回归保护，两版都通过）；Worker不传访客标识的变异版本使第1–3条失败。

## 待真机

- V1g：退出到游客，首页 → 分区逐个打开；首页 → 视频详情 → UP主页翻页。若失败，报告页面提示与“帮助与诊断”的“最近一次分区/UP投稿读取”一行。
- 设置 → 本机数据：确认状态为“已保存”，按“清除B站访客标识”后再打开一个分区。
- 回归：登录状态的分区、UP主页、导航。

## 0.51.3真机结果（2026-10-23）

- V1g USER PASS：游客状态下分区逐个打开、视频详情 → UP主页翻页均正常。
- 清除访客标识 USER PASS：设置 → 本机数据一键清除，之后分区照常读取。
- 登录状态回归 USER PASS：分区、UP主页、导航不变。
- 风控状态随同一出口变化；本结果不证明以后不会再出现-352。WBI仍未加。

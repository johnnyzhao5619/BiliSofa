# ADR-094：搜索混入课程行与AI字幕文件地址

2026-10-23；F03/F07、R15、U5。接0.47.1真机复验：S5 USER PASS；S1、S3 FAIL。仅在`--product-reading-fix2`（0.47.2）构建生效；源码共享部分（搜索解析、字幕地址规则）对之后重建的旧变体同样生效。状态：**0.47.2已签名并升级安装/启动（平台确认，不清数据）；用户复验S1/S3 USER PASS**（[证据](../design/evidence/2026-10-23-reading-fix2/README.md)）。

## 用户反馈与根本原因

**S1：两个字的词总是搜不到，四个字时通常能搜到；选词后的焦点落点不好。**

- 公开视频搜索会在结果里混入付费课程行（`type: "ketang"`，没有BV号，时长为空）。热门短词（如“美食”“游戏”）常带这类行，较长或较冷的词通常不带。
- 解析器`parseSearchBody`遇到任何非`video`行就把整页判为无效，界面显示“搜索暂时无法完成”，看起来就是搜不到。
- 已用与电视相同的匿名请求（同签名、UA、Referer，无Cookie）在本机核实：服务对2字和4字关键词都返回4行；“美食”“游戏”“我的世界”页含`ketang`行，旧解析器拒绝；新解析器各得3条视频。这是API证据，不是电视证据。
- 焦点：选中候选词后该按钮被禁用，焦点回退到键盘的A键。搜索失败时焦点就停在左上角的A。

**S3：字幕无法读取，显示`overlay.permission`（该视频有多条字幕轨）。**

- 当前登录后的AI字幕文件地址是`aisubtitle.hdslb.com/bfs/ai_subtitle/prod/<id>?auth_key=…`，`<id>`没有`.json`扩展名（公开社区资料，见证据页）。
- TS层`subtitleSource`和原生`overlay_subtitle_url`都要求以`.json`结尾。原有测试只用了合成的`.json`地址，从未用真实登录响应核对过。
- 只要有一条轨道地址不合规则，`parsePlayerMetadata`就让整个轨道列表失败，错误码是`permission`。所以有多条轨道也全部读不出来。
- 匿名请求拿不到字幕列表（需要登录），本机无法取得该视频的真实地址；结论待真机确认。

## 决定

- **搜索解析**：格式正确的其他行类型（小写字母/下划线，最多32字符，如`ketang`、`live`）跳过，不再让整页失败；类型缺失或格式异常仍判为无效。是否还有更多页按原始行数判断，不按跳过后的条数判断。
- **选词后焦点**：结果到达后仍然聚焦第一条结果。读取期间，以及搜索为空或失败时，焦点留在“搜索”键（紧挨候选词，也是重试入口），不再回到A。
- **字幕地址**：
  - CC字幕仍要求`/bfs/subtitle/…​.json`。
  - AI字幕允许`/bfs/ai_subtitle/`下不带扩展名的id，但不能以`/`结尾。
  - 主机白名单、仅https、无用户名/端口/片段、字符集、`..`与`%`检查都不变。
  - TS与原生两层规则一致。
- **单轨失败不连坐**：地址不在范围内的轨道跳过，其他轨道照常显示，轨道键保留原行序号。全部轨道都不在范围内时报`overlay.unsupported`，并显示“字幕文件地址格式暂不支持”，不再显示`permission`。
- **原生模块**：只改`overlay-read.c`的地址规则，重新链接到新目录`build/overlay-read-subtitle`（`tools/link-overlay-read.py --out`）。冻结的`build/overlay-read`与旧包不变。只有0.47.2变体从新目录打包；改源码后，旧变体再打包会按来源校验失败，这是预期的。

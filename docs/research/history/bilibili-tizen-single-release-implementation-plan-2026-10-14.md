## 1. 已确认的产品合同

用户确认：基本功能＋全部扩展功能＋官方投屏，全部在同一正式版本完成；GitHub 公共仓库开源，项目自有代码采用 MIT。

“官方投屏”定义为：用户使用未修改的中国大陆版 Bilibili 官方 Android 手机 App、iPhone App 或 iPad App，在其投屏入口发现接收端，发起电视播放并进行播放控制。本项目是独立的兼容接收端，不能把协议兼容描述为 Bilibili 官方认证。

只设一个正式发布目标 v1.0.0。内部任务、提交、PR、CI 构建和设备验证按依赖推进；不发布“基础版”“扩展版”或功能删减版，不把试验构建当交付。全部范围达到验收条件后才创建正式 Release。后续维护不改变本次一次性交付全部功能的要求。

本次是实施计划编制，尚未创建 GitHub 仓库或开始应用开发。计划中的仓库名暂定 `bili-samsung-tv`；实际创建时确定 owner、可用名称及版权署名。

## 3. 架构建议

推荐一个 GitHub 单仓库维护“电视 WGT＋自用局域网伴随服务”，两者与文档共同交付为同一个 v1.0.0。

此前直连方案适合验证基本观看。现在多账号、账号写操作和官方 App 投屏都属于发布必需项，建议将伴随服务作为完整方案基线，避免到开发后期再更换会话和网络架构。服务可在用户选定的常开 Mac、Linux 主机或 NAS 运行；部署位置在实施时确定。

电视端保持轻量界面、焦点、播放器和覆盖层。伴随服务负责用户主动扫码产生的会话、接口适配、投屏发现与控制、必要的 MPD/媒体交付。视频尽可能由电视直接访问 CDN；仅在请求头、清单或容器适配确实需要时中转。默认不引入视频转码。

| 模块 | 主要职责 |
| --- | --- |
| TvShell / FocusRouter | 遥控器、页面路由、返回栈、中文 IME、焦点恢复、网络和生命周期 |
| SessionService | 扫码、多账号隔离、失效/续期、退出、账号选择与会话保护 |
| BiliAdapter | 内容与个人接口、签名、分页、权限状态、明确错误、有限读取重试 |
| WriteCoordinator | 用户动作提交、幂等守卫、结果未知处理、状态回读；不重放不可撤销操作 |
| PlayerAdapter | AVPlay 与 Shaka/MSE、实际解码能力、画质/编码/音轨、时间轴和恢复 |
| OverlayTimeline | 弹幕与字幕调度、评论面板、播放状态同步 |
| CastReceiver / CastBridge | SSDP/DLNA/NirvanaControl 候选协议、发现、连接、播放命令和状态同步 |
| GatewayTransport | 电视到服务的配对与业务请求；HTTP MPD、必要的有范围限制的媒体代理 |
| Diagnostics | 匿名化故障信息、起播分段耗时、实际播放状态、用户主动导出 |

建议将新增模块写成 TypeScript，使用成熟轻量构建工具，目标引擎以本机确认的 Tizen 9 / Chromium 120 为准。现有 Tizen 播放模块先封装成适配器保持行为，再逐段迁移；避免重写播放器与扩展业务同步进行。伴随服务采用实施时仍受维护的 Node.js LTS。

复用固定源码版本：Tizen 项目 `76003faf3ae1a647a92c532b968e4896427530cb`；webOS 项目 `e38ed9a83f12d9561a2ecf129c30af615dfc1ee1`。分别审查并提取平台、解析、调度和协议代码，不直接拷贝两套应用拼装。上游更新通过独立 PR 核对，不在构建时自动下载并执行最新分支。

## 4. 官方投屏专项

### 已有线索

[三星 Smart View](https://developer.samsung.com/smarttv/develop/extension-libraries/smart-view-sdk/getting-started.html)要求实现发送端和接收端。它不能证明现有 Bilibili 官方手机 App 会自动发现我们写的 Smart View 接收应用。

webOS 项目的 [deviceProfile.js](https://github.com/asdf17128/bili-webos/blob/main/service/com.biliwebos.app.service/cast/deviceProfile.js)提供 SSDP/DLNA MediaRenderer 与 NirvanaControl 描述；[nvaSession.js](https://github.com/asdf17128/bili-webos/blob/main/service/com.biliwebos.app.service/cast/nvaSession.js)实现控制会话。其测试登记记录过国内官方 App 用户的投屏反馈。这是候选协议线索，不是三星本机或当前官方 App 版本的验证。

这些网络监听模块采用 Node 服务实现，不能直接在普通 Tizen Web widget 中运行。因此先由局域网服务广播接收端，电视通过向服务建立的受控连接接收播放命令并回报状态。是否能无服务实现同等能力，需另有明确平台证据，不能据标准 Web API 假设存在 UDP 监听服务。

### 开发与验收

1. 记录 Android/iPhone/iPad 官方 App 的实际版本；在本地开发接收端验证发现、连接、点播命令和状态协议，使用用户认可的测试内容。
2. 先验证官方 App 当前可用的 DLNA 路径；若不满足控制和内容语义，验证 NirvanaControl/NVA 路径。准确区分通用 UPnP 数据与私有协议字段。
3. 发现列表显示自己的项目名称和准确能力；审查上游设备描述中的官方厂商/机型字段。兼容性若依赖这类身份字段，需单独记录约束并评估合适的授权/接入方案，不能未经分析直接对外宣称是官方设备。
4. 手机官方 App→接收服务→电视播放；电视状态反向回传。定义 sessionId、commandId、内容 ID/URL、位置、状态和错误；旧投屏会话不控制新播放。
5. 明确控制所有权：投屏接管普通播放前电视确认或按用户设置处理；第二个发送端请求接管时给出提示；发送端账号与电视所选账号分别处理，不修改电视账号和历史归属。
6. 连接断开、重复命令、切集、跨缓冲跳转、停止、电视手动暂停/返回、服务重启分别测试。能发现设备不足以判定投屏完成。
7. 第一版最低前提是电视应用已打开、服务在线。自动唤醒/冷启动单独测试能力并准确展示；不能要求用户修改官方 App 或安装自制发送端作为验收替代。

同局域网发现常涉及组播与防火墙，安装文档应明确实际所需端口、网络和手机本地网络权限。控制协议不能保证所有路由器、官方 App 更新或地区内容都兼容；发布必须附真实测试矩阵。

## 7. 发布门槛

建立 `docs/acceptance.md`：每个 F 编号列测试场景、设备/固件/App版本、账号类型与地域条件、操作步骤、实际结果、脱敏证据、通过/失败/阻塞。

### 内容与账号

- 至少两账号完成隔离、切换、扫码失效、退出与重启；测试账号由用户选择，涉及真实写操作逐项选择测试内容与允许动作。
- 至少 30 个普通视频，另加可用的番剧、直播、4K/HDR样本，覆盖会员/非会员、无权限、删除和地区受限场景。
- 收藏/关注/稍后再看/评论/弹幕/投币在官方客户端回读；不可撤销动作限次，不采用可能消耗真实资源的无人值守循环。
- 双向历史同步记录更新时间与冲突策略。投屏发送者与电视账户不同，明确历史和互动归属，不自动借用另一账户的权益。

### 播放与遥控器

- 目标电视实测分辨率、解码、音画同步、HDR、速度和音轨；播放 URL / UI 标签或模拟器成功不能代替真实效果。
- 各入口只用方向、确认、返回可完成；播放/输入法/弹层/网络加载中均可退出；无双焦点和焦点丢失。
- 两小时以上混合播放耐久、快速切视频、多 P/合集连播、直播断流、切质量/速度、切应用、休眠/恢复和断网。
- 确认屏保策略：实际播放时正确控制屏保，离开播放恢复系统行为。

### 投屏
